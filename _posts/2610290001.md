The [KAIST Mobility Group](https://kaistmobilitygroup.com/) homepage opens with a big photo slider.
When you hit the arrow, the photo doesn't just fade. It gets pushed sideways, smeared, and the next photo slides in from the other side.
I wanted to know how that works, so I took it apart and rebuilt it here.

I didn't copy it one to one, though. Two things are different on purpose:

- The original smears the photo through a mosaic of random triangles, like shattered glass. Mine uses vertical ribs, like the fluted glass you see on cafe windows.
- The original also animates the title letter by letter and blocks the arrows until that animation is over. I dropped the text effects and made the transition interruptible. Click "next" five times in a row and the image keeps sliding, it never restarts.

Here it is. Click the arrows (spam them, that's the point), drag the photo sideways, or leave it alone and it moves on every 20 seconds.
The photos are the Chungking Express stills from my portfolio page.

## What the original is built with

The site runs WordPress with a paid theme called `blackdsn`.
The slider widget is `dsn_slider_project_three`, and its markup carries these attributes:

```html
<div class="main-slider ... dsn-webgl"
  data-dsn-option='{"direction":"horizontal","autoplay":{"delay":20000}, ...}'
  data-dsn-webgl='{"displacement":".../displacement/1.jpg","intensity":-2,"speed_in":1,"speed_out":1.2}'>
```

The interesting part is the `dsn-webgl` class.
Reading the theme scripts (`custom.js` and `dsn-grid.min.js`), the setup looks like this:

- Swiper keeps track of which slide is active. It doesn't actually show the photos, its container sits at `opacity: 0`.
- The photos come from a single Three.js canvas: one full-screen plane with a shader that blends two photos.
- Titles are split into one `<span>` per letter with Splitting.js and animated with a GSAP timeline.
- The "previous/next slide" labels at the bottom are two more Swiper instances using the `parallax` option.

That's five libraries: jQuery, Swiper, Three.js, GSAP and Splitting.
I didn't want to pull all of that into one blog post, so my version is plain HTML, CSS and JS with no dependencies.
WebGL is built into the browser, so I talked to it directly instead of going through Three.js.

## The transition: a displacement shader

This is where the look comes from.
`dsn-grid.min.js` has a module called `WebGLDistortionHoverEffects`, and this is its fragment shader (horizontal mode):

```glsl
vec2 uv = (vUv - vec2(0.5)) * resolution.zw + vec2(0.5);
vec4 d = texture2D(disp, uv);

vec2 distortedPosition  = vec2(uv.x + dispFactor * (d.r * effectFactor), uv.y);
vec2 distortedPosition2 = vec2(uv.x - (1.0 - dispFactor) * (d.r * effectFactor), uv.y);

vec4 t1 = texture2D(texture1, distortedPosition);
vec4 t2 = texture2D(texture2, distortedPosition2);
gl_FragColor = mix(t1, t2, dispFactor);
```

It's simpler than it looks.
`disp` is a grayscale texture. Every pixel shifts the photo along x by its brightness (`d.r`).
As `dispFactor` goes from 0 to 1, the outgoing photo gets pushed further and further, and the incoming one starts pushed the other way and settles back into place.
`mix` blends the two, so halfway through you see both photos broken up and offset against each other.

`effectFactor` comes from `intensity: -2` in the config.
That's a big number. A pixel with brightness 0.5 gets pushed by a full screen width, so early in the transition the original photo is barely recognizable.

The first line, `resolution.zw`, is the shader version of CSS `object-fit: cover`.
It compares the canvas aspect ratio with the photo's and crops whatever doesn't fit.

```js
const imageAspect = image.naturalHeight / image.naturalWidth
const cover = height / width > imageAspect
  ? [(width / height) * imageAspect, 1]
  : [1, height / width / imageAspect]
```

I kept this shader exactly as it is. Everything else I changed is about what goes into it.

## Ribs instead of triangles

The shape of the effect lives entirely in the displacement texture, not in the shader.
The original uses `displacement/1.jpg`, a 527×336 image of small triangles with random gray values. Random flat patches push random pieces of the photo by random amounts, which is why it looks like broken glass.

For fluted glass I wanted vertical strips instead.
Inside each rib the brightness ramps up from left to right, then drops back down at the start of the next rib.
So every strip shows a slice of the photo that's shifted a bit more on its right edge than on its left, and the slices don't line up at the seams. That's exactly how a ribbed window bends what's behind it.

The texture is drawn on a canvas at load time:

```js
for (let x = 0; x < width; x += 1) {
  const local = (x % ribWidth) / ribWidth
  const rounded = 0.5 - 0.5 * Math.cos(local * Math.PI)
  const value = Math.round((RIB_LOW + (RIB_HIGH - RIB_LOW) * rounded) * 255)
  context.fillStyle = `rgb(${value},${value},${value})`
  context.fillRect(x, 0, 1, map.height)
}
```

There are 18 ribs, and the brightness only goes from 0.02 to 0.3.
My first try used 0.15 to 0.75. With `intensity` at 2 that pushed some strips by more than a screen width, so they sampled past the edge of the photo and turned into dark smeared columns. Keeping the range small means each rib shifts its slice by a fraction of the width, which is what real fluted glass does.
A plain linear ramp looked like flat sawtooth slices. The cosine curve makes each rib lens-shaped, flat in the middle and steep near the edges, so the strips read as rounded glass.
The texture is only 4 pixels tall because nothing changes vertically. Texture sampling stretches it over the whole canvas anyway.

## Plugging WebGL in directly

Three.js wasn't doing much here.
One rectangle that covers the screen (two triangles), four textures (three photos and the rib map), and a handful of uniforms.
The vertex shader skips the camera and writes clip coordinates straight away:

```glsl
attribute vec2 position;
varying vec2 vUv;
void main() {
  vUv = position * 0.5 + 0.5;
  gl_Position = vec4(position, 0.0, 1.0);
}
```

After that it's just uploading the photos with `gl.createTexture()` and calling `drawArrays` once per frame with a new `dispFactor`.
The canvas is sized with `devicePixelRatio` so it stays sharp on retina screens.
If WebGL isn't available, it falls back to crossfading three `<img>` tags with the same progress value.

## Making it interruptible

In the original, each click starts a fresh 1.6 second tween from `dispFactor = 0` with an expo-out curve, and the arrows are locked while the title animation runs.
Click twice quickly and the second click either does nothing or snaps the image back to the start of a new tween.

I threw that out and described the whole slider with one number, `position`.
`0` is slide 1, `1` is slide 2, and `1.4` means 40% of the way from slide 2 to slide 3.
Rendering just reads the two slides around `position` and uses the fractional part as `dispFactor`:

```js
function render() {
  const base = Math.floor(position)
  renderer.draw(wrap(base), wrap(base + 1), position - base)
  showSlide(wrap(Math.round(position)))
}
```

Clicks never touch `position`. They only move `target` by one.
Every frame, `position` moves toward `target` in a straight line:

```js
const remaining = target - position
const speed = Math.max(1, Math.abs(remaining)) / SECONDS_PER_SLIDE
position += Math.sign(remaining) * Math.min(Math.abs(remaining), speed * seconds)
```

One slide takes 1.2 seconds. If you queue up three slides, the speed scales with the distance left, so it still arrives in about 1.2 seconds instead of making you wait 3.6.
Because the motion is linear and nothing ever resets, extra clicks just extend the slide. You can't break it by clicking.

`position` isn't wrapped, it keeps growing past the last slide, and `wrap()` maps it back onto the three photos. That's why the loop from slide 3 back to slide 1 looks the same as any other step.
Going backwards also falls out naturally: moving from 1.0 to 0.0 runs the same blend in reverse.

Dragging uses the same number.
While you drag, `position` follows your pointer (one full container width equals one slide).
When you let go, it rounds to the nearest slide, or moves on to the next one if you flicked quickly, and the same linear motion finishes the job.

## Text and the bottom bar

The title and description now just swap at the halfway point of the transition, with a plain 0.4 second opacity fade.
The labels in the bottom bar show the previous and next slide titles and update at the same moment.

The rest of the layout follows the original's computed styles:

- The slider padding is 90px top and bottom and 100px left and right (40px on tablets, 0 on phones), and the photo sits inside that.
- The lower half of the section has a black-to-gray gradient, and `box-shadow: 1px 0 31px 45px #101010` blurs out the bottom edge of the photo so it melts into the dark band.
- The title uses Excon 500 at 95px, oblique. The original loads it from Fontshare, which is free, so I did the same.
- The `01 / 3` counter is stretched with `scaleX(1.5)` and clipped with `clip-path: inset(0 0 0 20%)`. The half-missing "0" is the original design, not a bug. The arrow circles are clipped the same way.
- Each slide puts its own black overlay over the photo (20% or 50%), taken from the original `data-overlay` values.

The post column on this blog is narrow, so the demo lives in an iframe.
Inside the iframe the height is derived from the width instead of `100vh`, and it's reported to the parent page with `postMessage`.
The mouse wheel only reacts to horizontal scrolling. The original also listens to vertical scrolling, but embedded in the middle of a post that turns every scroll into a slide change.

## Takeaways

I expected a WebGL slider to be a lot of code.
The shader is about ten lines. Almost the entire look comes from one grayscale texture, and swapping triangles for ribs changed the whole feel without touching the shader at all.
The bigger change ended up being the motion. Treating the slider as one number that chases a target was less code than the original's timeline, and it's what makes rapid clicking feel smooth.
